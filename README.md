# Go Pet Shop

`Go Pet Shop` - это учебный backend-проект интернет-магазина товаров для питомцев на Go и PostgreSQL.

Главная цель проекта - не просто "поднять сервер", а пройти весь путь, который обычно встречается в реальном backend-приложении:

- описать структуру данных в базе;
- подключить PostgreSQL;
- настроить миграции;
- сделать HTTP API;
- научиться разделять код на слои;
- поработать с CRUD-операциями;
- добавить заказы и связанные сущности;
- оформить заказ в транзакции;
- получить историю и простую аналитику;
- покрыть ключевые части тестами.

Этот README написан максимально подробно и ориентирован на новичка. Если вы только начинаете изучать Go, REST API и базы данных, документ можно читать последовательно сверху вниз.

---

## Что это за проект простыми словами

Представьте обычный интернет-магазин для питомцев:

- есть пользователи;
- есть товары;
- пользователь оформляет заказ;
- в заказ входят позиции заказа;
- после оформления заказа нужно зафиксировать оплату;
- позже нужно уметь посмотреть историю покупок и понять, какие товары самые популярные.

Именно это и моделирует проект `Go Pet Shop`.

С технической стороны приложение:

1. принимает HTTP-запросы;
2. валидирует входные данные;
3. обращается в PostgreSQL;
4. сохраняет или читает данные;
5. возвращает JSON-ответ клиенту.

## Стек технологий

Ниже перечислено, что используется в проекте и зачем это нужно.

### Go

Основной язык разработки. На Go реализованы:

- HTTP-сервер;
- хендлеры;
- конфигурация;
- логирование;

Реляционная база данных, где хранятся:

- пользователи;
- товары;
- заказы;
- позиции заказов;
- финансовые транзакции.

Драйвер и клиент для работы с PostgreSQL из Go-кода.

Легковесный HTTP-роутер. Он связывает URL и HTTP-методы с нужными обработчиками.

Используется для удобной работы с JSON:

- декодирование тела запроса;
- отправка JSON-ответов.

### `cleanenv`

Помогает загружать конфигурацию из YAML-файлов и переменных окружения.

### `godotenv`

Подгружает переменные окружения из файла `.env`, чтобы локальная разработка была проще.

### `golang-migrate`

Отвечает за миграции базы данных. С его помощью можно:

- создать структуру таблиц;
- применить изменения к базе;
- поддерживать схему БД в предсказуемом состоянии.

### `Taskfile`

Позволяет запускать часто используемые команды коротко и одинаково для всей команды.

Например:


Набор линтеров для статического анализа кода. Нужен, чтобы раньше замечать:

- неиспользуемый код;
- подозрительные конструкции;
- ошибки присваивания;
- потенциальные проблемы в логике.

## Архитектурная идея проекта

Проект разбит на понятные уровни. Это важно: новичку часто кажется, что "можно писать все в `main.go`", но в более реальном приложении код разделяют по ответственности.

### 1. `cmd/`

Это точки входа в приложение.

- `cmd/app/main.go` - запускает основной HTTP-сервер.
- `cmd/migrator/main.go` - запускает миграции.

Идея простая: разные исполняемые программы живут отдельно, но используют общую внутреннюю логику проекта.

### 2. `internal/config/`

Здесь загружается конфигурация приложения:

- какой порт слушать;
- где находится база данных;
- какой таймаут использовать;
- в каком окружении запускается приложение.

### 3. `internal/handlers/`

Здесь живут HTTP-хендлеры - функции, которые принимают запросы и отдают ответы.

Например:

- получить список товаров;
- создать товар;
- обновить товар;
- проверить состояние сервера.

### 4. `internal/storage/`

Слой доступа к данным. Его задача - работать с PostgreSQL и ничего не знать про HTTP.

Например:

- выполнить SQL-запрос;
- прочитать строки из таблицы;
- вернуть Go-структуры назад в хендлер.

### 5. `internal/models/`

Здесь описываются структуры данных приложения:

- `Product`;
- `Customer`;
- `Order`;
- `OrderItem`.

Эти структуры используются между слоями проекта.

### 6. `migrations/`

SQL-файлы, которые создают и удаляют таблицы.

### 7. `config/`

Файлы конфигурации для разных окружений:

- `local.yaml` - локальный запуск;
- `dev.yaml` - запуск в Docker/разработке.

## Текущая база данных

В проекте есть миграция [`migrations/0001_create_tables.up.sql`](/Users/maxim/goOffer/go-pet-shop/migrations/0001_create_tables.up.sql), которая создает основные таблицы.

Ниже - объяснение каждой таблицы человеческим языком.

### Таблица `users`

Хранит пользователей магазина.

Поля:

- `id` - уникальный идентификатор пользователя;
- `name` - имя пользователя;
- `email` - email пользователя;
- индекс по `email` нужен для быстрого поиска;
- `email` уникален, чтобы нельзя было зарегистрировать двух пользователей с одним и тем же адресом.

### Таблица `products`

Хранит каталог товаров.

Поля:

- `id` - идентификатор товара;
- `name` - название товара;
- `price` - цена;
- `stock` - остаток на складе.

### Таблица `orders`

Хранит сам факт создания заказа.

Поля:

- `id` - идентификатор заказа;
- `user_email` - ссылка на пользователя через `users.email`;
- `total_price` - общая сумма заказа;
- `created_at` - дата и время создания заказа.

### Таблица `order_items`

Хранит позиции внутри заказа.

Поля:

- `id` - идентификатор позиции;
- `order_id` - ссылка на заказ;
- `product_id` - ссылка на товар;
- `quantity` - сколько единиц товара купили.

### Таблица `transactions`

Хранит информацию об оплате или финансовом событии, связанном с заказом.

Поля:

- `id` - идентификатор транзакции;
- `order_id` - ссылка на заказ;
- `amount` - сумма;
- `status` - статус транзакции;
- `created_at` - когда транзакция была создана.

## Как проходит запрос внутри приложения

Новичкам полезно представлять не только список файлов, но и путь запроса.

Например, приходит `POST /products`.

Дальше происходит примерно такая цепочка:

1. Запускается HTTP-сервер из [`cmd/app/main.go`](/Users/maxim/goOffer/go-pet-shop/cmd/app/main.go).
2. Роутер `chi` понимает, что запрос нужно передать в shop-хендлер.
3. Хендлер из [`internal/handlers/shop/handler.go`](/Users/maxim/goOffer/go-pet-shop/internal/handlers/shop/handler.go):
   - читает JSON из тела запроса;
   - валидирует поля;
   - вызывает storage-слой.
4. Storage из [`internal/storage/postgres/shop.go`](/Users/maxim/goOffer/go-pet-shop/internal/storage/postgres/shop.go) выполняет SQL `INSERT`.
5. PostgreSQL сохраняет запись.
6. Storage возвращает ID созданного товара.
7. Хендлер формирует JSON-ответ и отдает его клиенту.

Это и есть типичный backend-поток: `request -> handler -> storage -> DB -> response`.

## Версия `v3` - Checkout и транзакция

### Главная цель версии

Научиться делать атомарные операции в базе данных.

Оформление заказа - это лучший пример, где без транзакции легко испортить данные.

### Что должно происходить внутри `PlaceOrder`

Когда пользователь оформляет заказ, приложение должно:

1. начать транзакцию;
2. проверить остатки товара;
3. уменьшить `stock`;
4. создать запись заказа;
5. создать позиции заказа;
6. создать запись в таблице `transactions`;
7. сделать `COMMIT`, если все прошло успешно;
8. сделать `ROLLBACK`, если на любом шаге произошла ошибка.

### Почему транзакция здесь обязательна

Представьте ситуацию:

- заказ уже создался;
- часть позиций сохранилась;
- остаток товара уменьшился;
- а запись об оплате не создалась.

Без транзакции база окажется в неконсистентном состоянии.

С транзакцией либо сохраняется все, либо не сохраняется ничего.

### Какие SQL-навыки отрабатываются

- транзакции;
- конкурентное обновление остатков;
- проверки в `UPDATE`;
- обработка ошибок БД.

### Какие хендлеры ожидаются

- `POST /checkout`

### Что важно понять новичку

- транзакция - это не "дополнительная фича", а механизм защиты данных;
- бизнес-операции из нескольких шагов нельзя делать разрозненными запросами;
- остатки товара особенно чувствительны к ошибкам.

- аналитика почти всегда строится поверх `JOIN` и агрегатов.

## Пошаговый запуск проекта локально

Ниже - подробная инструкция, чтобы даже при первом запуске было понятно, что происходит.

### 1. Что должно быть установлено

Перед началом убедитесь, что у вас есть:

- Go;
- PostgreSQL;
- `task` (Taskfile runner);
- при необходимости `golangci-lint`;
- Git.

Проверить можно так:

```bash
go version
psql --version
task --version
golangci-lint --version
git --version
```

### 2. Клонирование проекта

```bash
git clone https://github.com/pavloging/go-pet-shop.git
cd go-pet-shop
```

### 3. Создание базы данных

Нужно создать PostgreSQL-базу, например `petshop`.

Пример через `psql`:

```sql
CREATE DATABASE petshop;
```

### 4. Создание файла `.env`

В корне проекта создайте файл `.env`.

Пример содержимого:

```env
DATABASE_URL=postgres://user:password@localhost:5432/petshop?sslmode=disable
```

Если вы запускаете проект через Docker Compose, дополнительно могут понадобиться переменные для контейнера PostgreSQL, например:

```env
POSTGRES_USER=user
POSTGRES_PASSWORD=password
POSTGRES_DB=petshop
DATABASE_URL=postgres://user:password@postgres:5432/petshop?sslmode=disable
```

### 5. Применение миграций

Проект использует команду:

```bash
task migrate
```

или:

```bash
task generate
```

Это одно и то же, потому что `migrate` указан как alias.

## Запуск через Docker Compose

- в контейнере адрес базы обычно не `localhost`, а имя сервиса, например `postgres`;
- порт приложения пробрасывается на `8080`.

## Конфигурация проекта

Конфигурация загружается из:

- YAML-файла в папке `config/`;
- переменных окружения;
- файла `.env`.

Логика находится в [`internal/config/config.go`](/Users/maxim/goOffer/go-pet-shop/internal/config/config.go).

### Как выбирается конфиг

Приложение смотрит на переменную `APP_ENV`:

- если она не указана, используется `local`;
- тогда читается файл `config/local.yaml`;
- если `APP_ENV=dev`, читается `config/dev.yaml`.

### Что находится в конфиге

- `env` - имя окружения;
- `http_server.address` - адрес и порт HTTP-сервера;
- `http_server.timeout` - таймаут обработки запросов;
- `http_server.idle_timeout` - idle timeout;
- `http_server.database_timeout` - таймаут для операций с БД.

### Почему `DATABASE_URL` берется отдельно

Подключение к базе часто отличается между локальной машиной, Docker и CI.
Поэтому строку подключения удобно держать в переменной окружения, а не зашивать в YAML.

## Какие линтеры используются и зачем они нужны

В задании указаны следующие проверки:

- `unused`
- `bodyclose`
- `govet`
- `staticcheck`
- `errcheck`
- `ineffassign`
- `gocyclo`

Если вы новичок, вот короткое объяснение:

- `unused` - ищет неиспользуемые переменные, функции, импорты;
- `bodyclose` - следит, чтобы HTTP body корректно закрывался;
- `govet` - базовая проверка подозрительных мест в Go-коде;
- `staticcheck` - очень полезный расширенный анализатор;
- `errcheck` - напоминает не игнорировать ошибки;
- `ineffassign` - ищет бессмысленные присваивания;
- `gocyclo` - следит, чтобы функция не становилась слишком сложной.

## Частые ошибки при выполнении такого проекта

### 1. Смешивание слоев

Например, когда SQL пишется прямо в хендлере.

Лучше разделять:

- хендлер знает про HTTP;
- storage знает про БД.

### 2. Отсутствие валидации

Если не проверять:

- пустое имя;
- отрицательную цену;
- отрицательный stock;

то в базе окажутся некорректные данные.

### 3. Отсутствие транзакции в checkout

Это одна из самых важных логических ошибок во всем проекте.

### 4. Слабое описание в README

Если README состоит только из двух команд, новичку и проверяющему сложно понять:

- что уже реализовано;
- как запускать проект;
- что относится к какой версии;
- зачем вообще нужна каждая часть.

### 5. Несоответствие README и кода

Документация должна отражать реальное состояние проекта. Если в README написано, что есть `/checkout`, а в коде его нет, это сбивает с толку.
